# ADR-0003 —— 中断是一条通知，令牌是它唯一诚实的形态

**状态：** 已接受（2026-11-09），已落地。取代 ADR-0002「未在此决定」一节里"逐请求取消不存在"那一行。

## 背景

ADR-0002 把通道建成这样：读循环从不运行 handler——它回答握手、把回复交给等它那个 id 的调用、把请求派给 worker。然后它记下一句：逐请求取消不存在，也没有被排除。

两件事让这个问题变具体了。aura 裁定停止是一个控制位、而它的第二级是 realm 掀在途操作（aura ADR-0047）；gravity 裁定被取消的 turn 不能是存储里的标记（gravity ADR-0008）。两者之间夹着的正是这条通道，问题因此变得很精确：*父进程不再等某个调用了——guest 怎么知道？*

## 决定

**1. 形态是通知，不是请求，也不是臂。** `{"type": "interrupt", "id": N}`。它不是 `Arm`，因为臂是 guest→host 的能力，而这条方向相反；它不是请求，因为没有任何东西要回答。读循环按固定顺序认领帧——`initialize` → 回复 → **中断** → 调用——三种形状互斥，所以这个顺序是读法，不是竞态（`an_interrupt_is_a_notice_the_reader_claims_before_the_call_arm`）。

**2. 能收到，是因为读循环是空闲的。** 帧由读循环认领，而读循环从不运行 handler——这是这个决定得以存在的结构性原因。卡在单次长操作里的 handler 不需要在"读"什么，读的是循环。

**3. 进了 guest，它变成一个 `CancelToken`。** 一个标志加 `wait(timeout)`，挂在 ctx 上。不是投递：handler 是 worker 线程上的普通函数，没有"投递"这个动作可做。也不是中止：运行中的线程不能被安全中止，声称可以的运行库是在骗 guest。

**4. 边界要写出来，不能藏。** 从不看令牌的 handler 从内部停不掉。外层边界是宿主的时钟——杀进程——那是载体的事，不是这个 crate 的事。令牌的职责是把便宜的那种情况变便宜；不许把它写成它兑现不了的保证。

**5. 早到的中断不会丢。** 串行 guest 会排队；中断可能指向一个还没开始的调用。读循环为该 id 留下一个已升起的令牌，worker 用 `entry().or_default()` 取到它，于是这个调用"一开始就是被取消的"，而不是迟了一步。迟到的中断——指向已经答完的调用——会留下一个已升起的令牌；这张表的大小由取消次数决定，不由流量决定。

## 后果

- **词表不动。** `Arm::ALL` 不受影响；`wire.rs` 里那条冻结词表的测试不挪。长出来的是一个帧类型，和宿主侧的 `Writer::interrupt(id, budget)`。
- **老 guest 会忽略它。** 早于本决定的 guest 把它当不可解码帧，打一行日志、保住链路——这正是"宿主发来的陌生帧"本来就有的行为。
- **线上没有"停成功了吗"这个事实。** 父进程自己的终局值就是答案；guest 若最终产出一个结果，丢弃即可。这与 aura 在调用边界上的选择是同一条，也正是"guest 不必为它可能没察觉的停止作报告"的原因。
