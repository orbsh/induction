# 0002 — 一次一帧是环路的走法，不是协议的形状

> **Languages:** [English](ADR-0002-concurrent-requests.md) (primary) · [中文](ADR-0002-concurrent-requests.zh-CN.md)

**Status:** Accepted (2026-11-02)——三步已落地；这条通道两端都能承载并发请求。
**Date:** 2026-10-31（2026-11-02 接受）

## Context

guest 是一个**驻留**进程，而且常常是整个 booth 类型共用的一个。ADR-0001 定了帧的格式，对"一个请求还悬着的时候进程能干什么"一个字没说——能不能接第二个请求、两个 handler 能不能同时跑、回应是否必须按请求到达的顺序回来。它也不必说：协议的职责是字节，进程自己的线程是进程自己的事。但协议确实说了它是**驻留**的——一个不回到上一个请求就不能接下一个的驻留扩展，是披着驻留外衣的一次性进程。

而今天这条通道，两端都是串行的：

- **host 侧。** `supervise.rs` 就是一个循环——读一行、`route_line(ops, &line).await`、写回应行——而 `ops.invoke(&call).await` 就摆在这个循环体里。一个要跑几分钟的调用会把该会话后续所有帧全堵住，包括跟它毫无关系的帧。
- **guest 侧。** `read_host_reply` 把通道上的**下一帧**当成本次请求的答案（`induction-guest/src/lib.rs`，"no host_reply" 是它除坏帧之外的唯一失败形态）。它从不看 id。

配对字段其实早就在了——只在一个方向上，而能用它的那一端不看它：`CallFrame`（host 的请求）带 `id: u64`（`induction-protocol/src/frame.rs`），guest 的回应是 `ResultFrame {"id": N, "result": …}`。这就是配对词汇，从第一版切片就声明着，而 `read_host_reply` 从不读它。反方向则完全没有词汇：guest 的 ctx 调用是 `{"host": {"type": …, "args": …}}`，host 回应 `{"host_reply": {"ok": …}}`——两侧都没有 id，因为在此之前两侧都不可能有两个调用在飞。

**让它浮出来的那一例。** gravity 的 turn 在第一条流还活着时开第二条 LLM 流——用户答案一条、同一不可变前缀上的压缩一条（gravity PLAN Phase 3）。两条流都从同一个 provider 进程拉，一次一帧，交替进行。在当前这条环路下，第二个 `iterate_start` 在第一次 pull 返回之前根本不会被**读**；就算被读了，guest 的回应读取器也会把为 A 流写下的答案交给 B 流的 pull。这两个都不是协议的缺陷，是环路假设了自己是独苗。

## Decision

**这条通道承载并发请求，`id` 负责配对。** 三步，按这个顺序。没有一步改动帧的形状；只有一个字段被新增，就在第 2 步，落在 guest 自己的调用信封上。

**1. host：一请求一路由，写端单一所有者。** 读循环为每一帧起一个路由并继续读；路由完成时，回应带上**该请求自己的 `id`** 写出。写端必须单一所有者，因为线上单位是"行"——两个写者会把字节交织，而不是把请求交织。（落地形态是在同一循环里维护 in-flight future 集合，而不是 spawn 任务：`HostOps` 是借用的 `dyn`，spawn 会逼每个宿主改用 `Arc` + `'static`，换不到任何并发。并发性一样，差别只在调度器住在哪。）

**2. guest：自己的读取者，按 id 配对回应。** 通道一分为二：读取线程（或任务）把回应解复用到 `HashMap<id, oneshot>`；一次往返只等**自己那个 id**。从不并发发起调用的 guest 完全不受影响——那张表永远只有一条，程序的形状一点不变。全场唯一新增字段就在 guest 的出栈调用上：它带上自己要等的 `id`，host 在 `host_reply` 里把它回显。这是加法，不是改形——两端解析器都忽略自己没读的键，所以旧 host 仍能服务新 guest，只是不能同时回应它的两个调用。

**3. 只有到这一步**，一个 booth 才能同时服务两个请求。协议里别的东西一件不动：`iterate` 的 pull 本来就按 `stream_id` 寻址，并发是进程的属性，不是流的属性。

**另一条路——把"回应按 FIFO 顺序"写进协议——被否掉。** 那等于让每一次长调用都变成整个会话的停摆，与"驻留"的含义相悖；也等于把一个调度策略塞进一个本不该有策略的格式里。

## Consequences

- **回应可以乱序到达。** 任何"下一帧就是我的答案"的假设，正是第 2 步要拿掉的东西；还在这么假设的 guest，是一个潜伏着错配的 guest。
- **慢 handler 不再堵住兄弟请求。** 它也不再天然是背压信号：host 现在可以往 guest 里堆任意多的工作，因此今天只给写做预算的地方，需要补一个按请求的超时。
- **写端必须保持单一所有者**，包括关闭路径——spawn 任务是简单的那个半场。
- **测试必须交错。** 现有 pair 测试一次一个请求，证明不了这里任何事。第一个值得写的测试是：两个请求，**后**发的那个先被回答。
- **故障的影响半径缩小了。** handler 返回错误早就不是致命的——它被当作回应写回去（`Routed::Reply(Reply::Error)`），坏帧也只是记一行日志跳过。今天真正致命的是 handler **panic**：它 panic 的是这个循环，会话随之死掉。一请求一任务之后，panic 被关在那个请求自己的任务里——调用方看到的是"这条通道什么都没答"，会话还活着；问题于是变成"一个请求的调用方在它的任务死掉时怎么办"，这是按请求回答的问题，不是按会话回答的问题。

## 已落地（2026-11-02）

- **host。** `run_driver` 自己在同一个循环里轮询 in-flight 路由（不引 futures crate，也不需要 `'static`），每条完成的回应都带上 `route_line_tagged` 从请求里取回的 id 写出。同时在飞的路由到 64 条就暂停读取——不等待的 guest 只会卡住自己，不会撑大宿主的内存。写端只有两个来源：回应与宿主事件帧，一个所有者。
- **guest。** 运行循环从不执行 handler：它答握手、把回应交给等这个 id 的调用（互斥量后面的 `HashMap<u64, Sender<Reply>>`）、把请求派给 worker。串行 guest（默认）只有**一个** worker 线程、按到达顺序；`Guest::concurrent(true)` 让每个请求各占一个线程。没有 id 的回应在只有一个调用在等时仍然能派出去——那是 ADR 之前的宿主，也是这次改动是加法而非破坏的原因。
- **线上形状。** guest 的调用是 `{"host": {"type": …, "id": N}}`，宿主回应 `{"host_reply": {"id": N, "ok"|"error": …}}`。两个键在旧解析器里都被忽略。
- **测试。** `two_requests_run_at_once_and_each_waits_on_its_own_reply`（guest crate，真实进程）：两个 handler、两个在飞的 ctx 调用，**后**到的请求先答完，且两次调用各带不同的 id。`the_driver_routes_two_guest_calls_at_once`（host crate，duplex）：慢路由不拖住快路由，两条回应都回显各自调用方的 id。

## Not decided here

- **没人拉的流由谁驱动。** `iterate` 是消费驱动的：没有 pull 就没有进展。一个在两次 turn 之间持有活流的驻留 guest，仍然需要一个活过请求入口的驱动者（常驻循环、定时器、队列）。那是调用方的设计，不是通道的。
- **公平性、优先级、按请求取消。** 一项都没有，也一项都没排除。一个永不回答的请求占着它的位置，直到调用方放弃。
- **guest 是否**应该**并发。** 本记录让它**可能**。想一次一个的 guest 自己拿一把锁就是了，那个选择本来就该在它自己手里。
